# Данные и обновления

## Файлы проекта

В `fixtures/receipt-bot/` лежит связанный пример. `project.json` описывает экран, узлы и связи. Поля x, y, width и height — координаты внутри полотна при 100%; начало координат сразу под заголовком проекта. Координаты узлов и `points` у связей необязательны. Без них приложение раскладывает граф само: основная цепочка слева направо, конфиг над своим получателем, исход-исключение под источником. Демопроект хранит координаты, чтобы совпадать с референсом.

Узлы типов action, config и outcome отрисовываются разными компонентами. Необязательное поле `icon` выбирает значок узла действия из набора input, http, logic, database, file; без него значка нет. `source` конфигурационного узла ссылается на соседний `promo.yaml`. Для условных переходов в edges заданы подпись и роль; полилинии используют ту же систему координат. Роль задаёт рисунок линии: default и alternate — сплошная, config — точки, exception — терракотовый штрих. Исход, в который входит связь с ролью exception, рисуется терракотовым.

`tests.json` задаёт группы, порядок подтестов, узел для подсветки и доменные подписи между группами. Состояние нового прогона для всех подтестов — waiting. Каталог можно построить на этапе сбора тестов; сопоставление pytest nodeid с узлом схемы публикуется явно. Порядок карточек отражает логику примера, реальное время исполнения берётся из журнала.

У подтеста есть `nodeId` и необязательный `edgeId`. Пока подтест идёт, подсвечиваются его узел, связь `edgeId` и узел, в который эта связь ведёт. Состояние узла выводится из его подтестов: идёт хотя бы один — синий; иначе упал хотя бы один — красная рамка с меткой «✕ упал»; иначе покой. Красная отметка держится до следующего run.started.

## Строка журнала

Каждая завершённая строка `run.jsonl` — отдельный JSON-объект. Общие поля: v=1, projectId, runId, seq, at (UTC ISO 8601), type. Номер seq начинается с 1 и возрастает внутри прогона.

| type | Дополнительные поля | Изменение |
|---|---|---|
| run.started | tool, branch | Создать новый прогон и очередь из каталога |
| test.started | testId | Перевести подтест в running. Нижняя строка получает его nodeid, схема — nodeId |
| test.finished | testId, status, при ошибке message | status равен passed, failed или skipped. Закрыть проверку, сохранить причину |
| run.finished | exitCode | Зафиксировать завершение. При прерывании явно показать, какие проверки не успели завершиться |

Если процесс прогона убит, run.finished не придёт, и интерфейс не угадывает исход. Когда есть идущая проверка, а новых событий нет дольше 60 секунд, строка CLI показывает «нет событий N с»; статусы не меняются. Прогон считается прерванным, когда run.finished приходит при незавершённых проверках (например, после Ctrl+C pytest успевает закрыть сессию): идущая проверка получает «Прерван», ожидавшие — «Не запускался».

Ключ уникальности события — пара (runId, seq). Счётчик «пройдено» учитывает только passed; упавшие показаны рядом отдельно: «9 из 10 пройдено · 1 упал». Для подписи группы «1 / 2» числитель — число завершённых проверок. Боковая панель показывает все собранные подтесты, включая waiting. Цвет состояния дублируется текстом или иконкой. При параллельных тестах каждый сохраняет собственный статус. В строке активности можно показывать последний активный тест и количество остальных.

## Локальное подключение для MVP

- `GET /api/session` возвращает project, каталог suites, снимок run с состояниями всех подтестов, lastSeq и текущий режим demo/live. Конфиг отдаётся вместе со снимком как прочитанный текст. Сервер привязывается к localhost.
- `GET /api/events?runId=…&after=…` продолжает поток после lastSeq. Транспорт — Server-Sent Events; SSE id имеет вид runId:seq. Сервер сначала отдаёт пропущенные записи, затем новые в порядке seq, без зазора между чтением истории и подпиской.
- reducer игнорирует уже применённые номера того же прогона. При пропущенном номере, смене runId, ротации журнала или смене описания проекта клиент запрашивает свежий снимок. Обновление данных сохраняет камеру.
- Адаптер пишет полный объект и перевод строки. Читатель ждёт завершения последней строки. Повреждённая завершённая строка переводит источник в состояние ошибки с номером строки.
- Для CLI-прогона pytest адаптер учитывает setup, call и teardown; итоговый статус теста публикуется после завершения последней фазы. Повторный запуск всего набора получает новый runId. Для первого живого примера достаточно одного процесса записи.

## Контрольные точки демо

- После seq=1 все 10 подтестов ожидают.
- После seq=16 семь пройдены, проверка duplicate выполняется, обе проверки ответа ожидают. Это кадр референса.
- После seq=22 прогон окончен. Повторный чек сохранился в единственном экземпляре, однако тест текста ответа упал. Причина находится в message события seq=21.
- Для визуального сравнения используйте тот же reducer со срезом журнала. Для воспроизведения используйте полный журнал и интервалы между at.
